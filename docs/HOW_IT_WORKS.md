# 무엇을 어떻게 만들었는지

## 먼저 알아둘 세 가지

이 키트에는 **찾아 쓰는 목록**, **실행해 보는 업무 실험실**, **새 프로젝트로 복사하는 시작 도구**가 있다. 28개 레포를 모두 하나의 제품에 넣지 않았다. 일상적인 업무 흐름에 필요한 작은 부분을 연결했고, 다른 문제에는 맞는 예제를 선택한다.

기본 실험실의 분류는 키워드 규칙이다. Pydantic AI 연결 코드는 따로 있고, 실제 SDK의 테스트 모델로 호출·출력 검증 경로를 시험했다. 외부 유료 모델은 호출하지 않았다. 따라서 화면에서 "규칙 기반"으로 표시되는 결과를 AI 성능으로 설명하면 안 된다.

실행 버튼은 이 기기의 SQLite에 결과를 남긴다. 환불·구매·시설 조치를 실제로 수행하지 않는다. 실제 서비스에 연결할 때 교체할 지점은 분명하지만 그 연동이 이미 구현됐다는 뜻은 아니다.

## 문의 한 건이 지나가는 길

예를 들어 "주문 DEMO-001을 반품하고 싶어요"를 입력하면 다음 순서로 움직인다.

1. `runtime/web/app.js`가 요청과 중복 방지용 요청 키를 서버로 보낸다.
2. `runtime/app.py`가 토큰에 연결된 작업공간·역할을 확인하고 입력을 검사한다.
3. `domain_packs/support.json`에서 분류 기준과 정책을 가져온다.
4. `runtime/providers.py`가 초안을 만든다. 모델 모드에서는 Pydantic AI가 정해진 형식으로 결과를 받는다.
5. `runtime/store.py`가 초안·해시·버전·처리 이력을 SQLite에 저장한다.
6. 사용자가 승인하면 그 시점의 초안 해시를 승인 기록에 묶는다.
7. 실행할 때 현재 해시·버전·승인을 다시 검사하고 로컬 결과를 한 번 기록한다.

**해시**는 내용이 같은지 비교하는 지문이다. **버전**은 사용자가 보고 있는 요청이 최신인지 비교하는 번호다. 둘 다 필요하다. 입력을 바꿨는데 규칙이 우연히 같은 초안을 만들더라도 버전은 바뀌고 승인은 해제된다.

## 재사용할 때 바꾸는 곳

| 바꾸려는 것 | 파일 | 그대로 쓰는 부분 |
|---|---|---|
| 고객 문의를 시설/구매 업무로 | `domain_packs/*.json` | API, UI 흐름, 승인·실행·이력 |
| 규칙을 모델 추론으로 | `runtime/providers.py`와 모델 설정 | 결과 형식, 정책 ID 검증, 검토 UI |
| 로컬 기록을 실제 업무 시스템으로 | `runtime/store.py`의 로컬 실행 경계부터 별도 어댑터 설계 | 승인된 내용·권한·요청 ID의 계약 |
| 웹 화면을 모바일/CLI로 | 클라이언트 | HTTP API와 서버의 업무 규칙 |
| 분석·검색·배정 문제로 | `runtime/capabilities.py`의 해당 어댑터 | 작은 실행 예제와 입력·결과 검증 방식 |

도메인 팩은 단순 문구 바꾸기만으로 현업에 완성되는 것은 아니다. 분류 체계, 필요한 필드, 예외, 승인권자, 근거 자료와 정답 사례를 도메인 담당자와 채워야 한다.

## 직접 만든 것과 재사용한 것

- FastAPI/Pydantic: HTTP API, 입력·출력 형식 검증.
- Pydantic AI: 모델 호출과 구조화 응답. 자체 LLM SDK를 만들지 않았다.
- SQLite: 저장·트랜잭션·고유 제약·온라인 백업. 자체 데이터베이스를 만들지 않았다.
- MarkItDown: 텍스트 변환. 현재 예제는 합성 텍스트와 키워드 검색 기준선이다.
- DuckDB: 고정 SQL 집계. 모델이 계산 결과를 임의로 만들지 않는다.
- OR-Tools: 제약을 만족하는 일정 계산과 불가능 판정.
- 직접 만든 부분: 도메인 규칙 연결, 승인·버전 처리, 검토 UI, 작은 어댑터, 시작 도구와 검증·설명 자료.

FastAPI Full Stack Template 전체를 포크한 제품은 아니다. 로그인·PostgreSQL·Docker·프런트엔드 빌드 체인까지 필요한 제품을 만들 때 검토할 후보로 남겨 두고, 여기서는 FastAPI 라이브러리 위에 작은 로컬 참조 구현을 만들었다.

## 현재 깨질 수 있는 곳

- 규칙은 새 표현·부정문·복합 의도를 잘 이해하지 못한다. s11의 분류 불일치가 실제 예다.
- 구조화 응답 검증과 근거 ID 검사로 사실 정확성까지 보장하지 못한다.
- 정책 ID는 업무 기준의 참조다. 모든 설명 문장이 그 기준에 논리적으로 뒷받침되는지는 별도 평가가 필요하다.
- 기본 브라우저는 로컬 운영자 권한이다. 공개 서비스용 로그인·다중 사용자 인증은 구현하지 않았다. 로컬 접근 가능한 다른 사용자도 화면을 사용할 수 있다.
- SQLite 로컬 기록의 중복 방지는 외부 결제·이메일의 정확히 한 번 실행을 보장하지 않는다.
- 일일 호출 수는 제한하지만 달러 비용의 하드 캡은 구현하지 않았다. 모델별 가격과 사용량을 연결해야 한다.
- DB 변경 마이그레이션, 대규모 큐, 운영 배포, 장치 권한, 실시간 음성은 기본 실험실 범위 밖이다.

이 목록은 사용을 막기 위한 것이 아니라 확장할 때 어디를 검증해야 하는지 알려주는 지도다.
