# 해커톤 전 준비와 당일 실행 순서

행사명·공고는 아직 주어지지 않았다. 아래는 범용 준비안이며, 기존 코드와 AI 생성물 반입 허용 여부는 확인되지 않았다.

## 가져갈 준비물

| 준비물 | 지금 상태 | 행사 전 완료 조건 |
|---|---|---|
| 레포 후보·선택 이유 | 28개 조사 완료 | 주력 베이스 1개와 보조 2개로 축소 |
| 문제별 레시피 | 8개 준비 | 주제에 맞는 하나 선택 |
| 문제 정의·도메인 규칙 | 템플릿 준비 | 실제 사용자·실패 비용·제약 채우기 |
| 합성 데이터 | 고객 문의 샘플 12개와 평가 틀 준비 | 실제 주제에 맞춰 정상 10건 이상과 경계/실패 사례 제작 |
| 실행 환경 | 로컬 업무 실험실과 4개 예제 검증 | 행사에서 선택한 실제 모델·외부 시스템을 추가 검증 |
| API 키·쿼터·예산 | 미연결 | 사용 계정·모델 권한·잔액·차단 한도 확인 |
| 오프라인 대안 | 규칙 모드와 모델 오류 대안 테스트, 설치 캐시 준비 | 행사 장비와 선택 모델의 오프라인 재시작 |
| 발표·증거 | 3분 시나리오 준비 | 실제 영상·측정값·링크 채우기 |
| 백업·복구 | ZIP 도구와 초기/완료본 | 새 폴더에 복구 후 실행 확인 |

## 공고에서 먼저 확인

- 사전 제작 코드·오픈소스·AI 생성 코드 사용 가능 범위와 사전 공개 의무.
- 개발 시작 시점, 팀 구성, 필수 제공 API/모델/데이터, 외부 유료 API 허용 여부.
- 심사 기준과 제출물: GitHub 공개 여부, 라이선스, 영상 길이, 발표 시간, 마감 시간대.
- 네트워크·GPU·전원·모바일 장치 조건과 모델/데이터 다운로드 가능 여부.

허용 규정이 나오기 전에는 이 키트를 연구 자료로 유지한다. 반입 금지라면 후보 조사와 숙련만 활용하고 행사 코드 작성 시점을 구분한다.

## 행사 전에 한 번 끝내둘 리허설

1. 주력 경로 하나 선택: 데이터 데모는 Streamlit/DuckDB, 업무 제품은 FastAPI template, TS 채팅은 AI SDK.
2. 공식 README를 따라 **선택한 버전**을 설치하고 lockfile·런타임·OS를 기록한다. 이 키트는 임의의 최신 설치 명령을 대신 실행하지 않는다.
3. 실제 모델에 작은 요청 한 번, DB 읽기/쓰기 한 번, 실패·timeout 한 번을 시험한다.
4. 반입이 허용되면 필요한 모델·패키지·샘플만 로컬 캐시에 준비하고 오프라인 재시작한다.
5. 다른 빈 폴더에 복구하고 동일 명령으로 실행한다. 성공 로그와 화면을 남긴다.

설치에 30분 이상 막히면 익숙한 대안으로 전환한다는 운영 기준을 권한다. GPU·실시간 음성·무거운 ERP 설치는 주제의 핵심일 때만 선택한다. 30분은 성능 예측이 아니라 시간 배분 기준이다.

## 24시간 행사라면

| 시간 | 목표 | 종료 조건 |
|---|---|---|
| 0–1h | 문제·규정·데이터·평가 합의 | 한 사용자, 한 핵심 행동, 정답 사례 확보 |
| 1–3h | 가장 작은 전체 흐름 | 입력부터 결과까지 실제 동작 |
| 3–8h | 핵심 도메인 기능 | 기준선보다 나아진 사례와 실패 사례 설명 |
| 8–12h | 권한·재시도·모델 오류 처리 | 승인 거부·중복·timeout 검증 |
| 12–16h | 사용 흐름·배포 또는 로컬 시연 | 새 세션에서 재시작 가능 |
| 16–20h | 평가·데모·영상 | 수치·근거·오프라인 대안 확보 |
| 20–24h | 제출·리허설·완충 | 제출 상태 확인 및 최종 백업 |

48시간이라도 첫 전체 흐름을 다음 날로 미루지 않는다. 팀이 여러 명이면 사용자 흐름, 데이터/업무 규칙, 모델/평가, 배포/발표로 책임을 나누되 API 형식과 데모 입력을 먼저 합의한다.
